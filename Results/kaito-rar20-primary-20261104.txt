RAR2 / RAR4 unpack-version 20 short-code lookup (2026-11-04)

Candidate
- RAR20HuffmanTable adds a 1,024-entry UInt32 primary lookup for codes of 1...10 bits. Records are (bitCount << 16) | (symbol + 1), with zero reserved for a long/invalid prefix.
- Long and invalid codes retain the original canonical 1...15-bit decoding loop. Table build still accepts the same incomplete trees and rejects oversubscription before publishing new canonical arrays.
- The primary table is allocated once per table and released in deinit. Canonical-code bounds limit every write to the 1,024 entries; only the unused suffix is cleared on rebuild.
- MSBFirstBitReader.peekPadded refills without setting overrun for lookahead padding. The actual symbol-width consume retains the original truncation behavior. Empty input and truncated long codes are covered by the new regression test.
- No third-party decoder source or disassembly was used. Inputs are the project's own RAR 2.50 fixtures and format notes.

Performance corpus and method
- The four checked-in, project-created RAR 2.50 fixtures: autorej, audio, biglz, solid. Their .b64 contents were decoded to .rar in temporary directories.
- Scripts/benchmark_kaito_inprocess.py, kaito bench --threads 1, 200 extractions per timing, four alternating timings per executable. Archive-open time is excluded; actual entry reads, table construction, model updates and CRC checks are included.
- This is a four-fixture benchmark, not a claim about every RAR2 workload. No new large RAR2 corpus was generated in this pass.
